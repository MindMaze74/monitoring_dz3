## 1. Краткое описание (Executive Summary)
21 октября 2018 года в 22:52 UTC в результате плановых работ по замене вышедшего из строя сетевого оборудования произошло кратковременное (длительностью 43 секунды) нарушение сетевой связности между сетевым концентратором и основным центром обработки данных (ЦОД) на восточном побережье США. 

Этот, казалось бы, незначительный сбой запустил цепочку событий, которая привела к рассинхронизации кластеров баз данных и общей деградации сервисов GitHub продолжительностью более 24 часов.

> **Ключевой принцип:** В данном инциденте мы сознательно выбрали **целостность данных (Data Integrity)** в ущерб **доступности (Availability)**. Мы приостановили работу части сервисов, чтобы предотвратить потерю пользовательских данных.

---

## 2. Воздействие (Impact)
*   **Пользователи:** В течение суток пользователи видели устаревшую или противоречивую информацию на сайте. Была нарушена работа с issues, pull requests и комментариями.
*   **Сервисы:** Наблюдались сбои в доставке Webhooks и сборке сайтов GitHub Pages.
*   **Данные:** Исходный код в Git-репозиториях **не пострадал**. Инцидент затронул только метаданные, хранящиеся в кластерах MySQL (авторизация, задачи, PR).

---

## 3. Причина инцидента (Root Cause Analysis)
**Корневая причина** носила системный характер (Blameless) и заключалась в непредвиденном поведении системы управления кластерами БД:
1.  **Триггер:** 43-секундный разрыв сети.
2.  **Поведение Orchestrator:** Инструмент `Orchestrator` (управляющий топологией MySQL на базе Raft) потерял кворум в восточном ЦОД и инициировал автоматический фейловер (переключение) на западный ЦОД.
3.  **Split-brain (Расщепление сознания):** Когда сеть восстановилась, выяснилось, что в базах на восточном побережье успели появиться записи, которые не были реплицированы на запад. Возникла ситуация, при которой автоматический возврат к исходной топологии был невозможен без потери данных.

## 5. Реагирование и Восстановление
*   **Коммуникация:** Была оперативно задействована статус-страница. Мы информировали пользователей о том, что приоритетом является сохранность их данных, а не скорость восстановления сервиса.
*   **Ручное вмешательство:** Инженеры вручную управляли топологией кластеров, чтобы предотвратить автоматические действия `Orchestrator`, которые могли усугубить ситуацию.
*   **Дренаж очередей:** После восстановления БД потребовалось значительное время на обработку накопившихся событий (Webhooks), чтобы не перегрузить инфраструктуру.

## 6. Уроки и последующие действия (Action Items)
Мы провели детальный разбор (Post-Mortem Review) с участием всех причастных команд. 

**Что сработало хорошо:**
*   Слаженная работа дежурной смены и быстрая эскалация.
*   Четкое следование принципу приоритета целостности данных.
*   Наличие актуальных резервных копий.

**Что нужно улучшить (Action Items):**
1.  **Настройка Orchestrator:** Изменить конфигурацию, чтобы инструмент не мог автоматически повышать статус первичных БД за пределы региона (Cross-region failover). *(Приоритет: P0)*
2.  **Улучшение Status Page:** Ускорить миграцию на новый механизм отчетности, который позволяет отображать статус отдельных компонентов, а не только общий цвет. *(Приоритет: P1)*
3.  **Переход на Active/Active:** Инициировать архитектурный проект по переходу на схему с несколькими активными ЦОД для обеспечения отказоустойчивости на уровне дата-центров. *(Приоритет: P1)*
4.  **Chaos Engineering:** Внедрить практики намеренного внесения сбоев (Fault Injection) в тестовой среде для проверки поведения `Orchestrator` при потере сети. *(Приоритет: P2)*
